# Design system

Reclaim's semantic CSS tokens live in `src/theme.css`. Components use shared surface, text, border, accent, spacing, radius, shadow, and control tokens. Light is the default presentation; light, dark, and system preferences are saved in SQLite.

The desktop frame uses persistent left navigation, compact topbar, content region, and contextual item drawer. Forms use shared field components and explicit labels; buttons have primary, secondary, quiet, and icon variants. Status and secure-storage indicators combine text with color. Responsive rules adapt navigation, grids, and forms for narrower windows. Reduced-motion preferences are respected and interactive controls have focus-visible styling.

Region sizing rules that follow from the 2026-11-06 layout repairs: the item drawer scrolls as a whole; the custody-history timeline keeps its natural height (bounded by its own internal scroll) instead of being flex-squashed, because a collapsed scroll container both hides content and becomes an invisible keyboard focus target in Chromium. Dashboard quick-action tracks use `minmax(0,1fr)` with wrapping labels, inventory toolbar controls wrap to a second row rather than clipping behind the panel edge, and lost-report actions are explicitly placed in the content columns at narrow widths. Operation feedback uses `inline-status` for success and `inline-alert` for errors, each with a matching `role`.

New UI should use semantic tokens rather than one-off color values and should preserve predictable headings, descriptions, and action alignment. Avoid using color alone to convey a status. Organization branding includes a persisted logo and accessible primary color. Onboarding and the main shell share a stored theme preference; Follow System uses OS preference CSS.

Text defaults to a 12 px minimum and uses a persisted interface-size preference. The small-A and large-A controls are in the top-right of setup and the main workspace; they adjust text and primary control targets and remain keyboard-operable with explicit accessible names.

Run `pnpm check:design` before merging UI changes. It scans component CSS and TS/TSX for unapproved color literals, while allowing `src/theme.css` to define semantic theme values and `src/theme-palette.ts` to define the curated organization palette. It also applies a heuristic check to JSX buttons and form controls for an explicit accessible name, text content, or wrapping label. This caught an unlabeled storage-message dismiss button; it now has a contextual accessible name. The check does not calculate computed accessible names, inspect screenshots, establish rendered contrast, or replace the visual qualification matrix in `docs/release-readiness.md`.

Run `pnpm check:contrast` for the token-level WCAG contrast checks. It covers core text on theme surfaces, field placeholders, status text, every curated organization brand and hover fill — including text on the brand-tinted `--brand-soft` selected-item surface — and focus-indicator contrast: 146 token pairs. Current checked light-theme minima include muted text 4.83:1, green status text 4.9:1 (darkened 2026-11-07 after the rendered axe sweep measured 4.45:1 on the setup canvas), blue status text 4.54:1, and warning text 4.53:1. Dark-theme field placeholder text is at least 5.0:1. White or dark text on curated brand fills and focus rings pass the script's thresholds in both themes. An axe-core rendered sweep across 70 screen/theme scans (2026-11-07) reports zero violations at every severity; see `docs/testing.md` for the fixed findings.

Disabled text remains intentionally subdued. The check does not include disabled content, photo overlays, user-provided colors, every rendered component/background pairing, native dialog chrome, screenshots at all scales, or assistive-technology output. Keep the full rendered contrast and accessibility review open until those cases are inspected.
